## 1. ข้อมูลที่ต้องสร้าง (family ใหม่ใน `gen_sft3.py`, ขับแอปจริงผ่าน MCP เหมือน SFT2)

| # | family | จำนวนแถว (ประมาณ) | เนื้อหา |
|---|---|---|---|
| 1.1 | `probe_bits` (แทน `probe` / `probe_group` เดิม) | 150 | ผู้ใช้พูดเป็นบิต / ช่วง ("sw0 ถึง sw3 เป็น 1", "เปิด sw1 กับ sw3", "a=1 b=0") → ป้อน **แยกบิตหรือช่วง** `{"sw[3:0]":"1111"}` / `{"sw1":1,"sw3":1}` ไม่มีการคิดเลข · กลุ่มเป็นเลข `{"sw":"0x0F"}` เฉพาะเมื่อผู้ใช้ให้เลขมาเอง · คำตอบ**ยกค่าจาก `inputs`/`outputs` ที่ probe คืน** · ลบประโยควงเล็บเล่าบิตที่คำนวณไว้ล่วงหน้าแบบ SFT2 ออกทั้งหมด · ผสมคำถามที่คำตอบคือ "ติด" และ "ไม่ติด" ครึ่งต่อครึ่ง |
| 1.2 | `stop_after_check` | 120 | ตรวจรอบเดียวแล้วตอบทันที (build → check+simulate → ตอบ) · แถวที่ผล tool มี `unchanged` หรือ "rebuilding changed nothing" → ตอบเลย (assistant ที่เรียกซ้ำก่อนหน้าเป็น `weight 0`) · งานถาม/อ่านอย่างเดียว (get_pins, explain) ไม่ต้อง simulate |
| 1.3 | `edit_report` | 150 | งานแก้หลายแบบ: เปลี่ยนชื่อขา (update_component), แก้ params, add/delete component, connect / disconnect, apply, set_pins → คำตอบขึ้นต้นด้วยสิ่งที่ทำจริง ("เปลี่ยนชื่อ err เป็น err_led แล้ว", "ลบ …", "ต่อ … เข้ากับ …") ตามผล tool · **คำตอบท้ายหลายรูปแบบ** (สั้น/รายการ/มีหรือไม่มีผลตรวจ) อย่างน้อย 6 แม่แบบต่อ family สุ่มจาก seed |
| 1.4 | `tool_cover` | 200 | tool ที่ SFT2 ไม่ได้สอน: `update_component`, `add_component`, `connect`, `disconnect`, `apply`, `simulate {vectors}`, `verify_truth_table`, `explain_simulation`, `get_pins`, `board_check`, `use_module`, `save_module`, `search_course` — อย่างละ ~15 แถว งานจริงที่ tool นั้นเป็นคำตอบที่ถูก |
| 1.5 | `dup_blocks` | 80 | บล็อกชนิดเดียวกันหลายตัวในงานประกอบ (div5 ×2, adder4 ×2 → 8 บิต, mux2 ×3 → mux4, counter_digit ×2): ตั้งชื่อ `d5a`/`d5b` แล้ว connect อ้างชื่อที่ตั้งเอง · มีแถวกู้ตัวจาก error "no block 'd0'" |
| 1.6 | `locked` | 30 | build ลงแผ่นที่ล็อก → error "locked for the agent" → สร้างลงแผ่นใหม่ (`<name>_new`) แล้วบอกผู้ใช้ว่าแผ่นเดิมถูกล็อก ไม่แตะ |
| 1.7 | `sim_cycles` | 40 | ตัวหาร/ตัวนับ N → `simulate {cycles: ≥ 2N+4}` แล้วอ่านคาบจาก `summary` (`period`, `duty`) ในคำตอบ |
| 1.8 | `user_log` | ตามที่มี | `from_logs.py` (โฟลเดอร์นี้): run ที่ผู้ใช้กด 👍 และแอปไม่ติด ⚠ → แถวเทรน · 👎 → `logs_bad.jsonl` ไว้ดูด้วยมือ (ห้ามเทรนตรง ๆ) |
| — | replay | 30–40 % ของ mix | SFT2 (`sft2_v2`) + SFT1 replay สุ่มตามสัดส่วน category |

กติกาเดิมที่ยังใช้: ทุก call รันในแอปจริง, ความผิดที่ใส่ให้เห็นก่อนกู้ตัว = `weight 0`, render ผ่าน template prefix-stable, ปิด thinking

## 2. การวัดผล (ทำก่อนเทรน ใช้วัด SFT2 เป็น baseline)
1. **eval_format ขยายเป็น ~30 เคส** แยกชุด hold-out: ถ้อยคำ ชื่อแผ่น ตัวเลข ไม่ซ้ำกับข้อมูลเทรน (เพิ่ม: probe_bits ×3, stop_after_check ×2, edit_report ×3, dup_blocks ×2, locked ×1, tool_cover ×5)
2. **eval ปลายทาง (`eval_e2e.py`)**: สั่งผ่าน `ai_chat` ทั้งลูป แล้วตรวจด้วยสคริปต์ — คาบจริงของวงจร, `check` 0 error, แผ่นอื่นไม่ถูกแตะ (hash ก่อน/หลัง), คำตอบตรงกับผล tool (ใช้ ⚠ ของแอปเป็นตัวนับ: คำตอบที่แอปติด ⚠ = ไม่ผ่าน), จำนวนรอบ/เวลา · 15 งานจากเทส A–D ของรายงาน + งานแลป
3. เป้า: eval_format ≥ 90 % บน hold-out, e2e ไม่มีงานไหนแตะแผ่นอื่น, ⚠ จากแอป ≤ 1 ใน 15

## 3. การเทรน
- base = **SFT2** (HF ที่ merge แล้ว) · QLoRA เหมือนเดิม · `--max_length 16384` (แอปเปิด ctx 24K แล้ว prompt จริง ≤ 14K)
- lr **5e-5** (ต่ำกว่ารอบก่อน — รอบที่ 3 บนตัวเดิม เสี่ยงลืม) · epochs 2 · replay 30–40 %
- ตรวจ mask ด้วย `--inspect` ก่อนเทรนทุกครั้ง
